## 새 API

모든 경로는 `/.netlify/functions/` 아래이다. 모든 응답은 JSON, no-store, Vary: Cookie,
noindex이며 CORS 허용 헤더를 추가하지 않는다. POST는 허용된 사이트 Origin과 JSON만 받는다.

| 경로 | 메서드 | 기능 |
| --- | --- | --- |
| `member-login` | POST | JSON `{id,password}` 확인 후 회원 쿠키 발급. 쿠키는 Set-Cookie에만 포함 |
| `member-session` | GET | 회원 쿠키·현재 계정 상태·현재 비밀번호 버전 재확인. 본인 ID만 반환 |
| `member-logout` | POST | 회원 쿠키만 만료. 관리자 쿠키/회원 기록/DB는 변경하지 않음 |
| `member-data?resource=account` | GET | 본인 계정의 명시적 공개 필드만 반환 |
| `member-data?resource=history` | GET | 본인 보관함 목록, 저장 HTML 제외 |
| `member-data?resource=reading&readingId=...` | GET | 본인 보관함의 해당 기록만 반환. 다른 회원 기록 ID는 404 |
| `member-data?resource=consultations` | GET | 서버 logs에 존재하는 본인 상담 메시지만 반환 |

외부 요청의 회원 ID/테이블/필터는 받지 않는다. 권한 판단과 자료 추출은 같은 DB 응답에서
수행하며, 원본 회원·로그 객체를 응답에 펼치지 않는다. 다른 사용자와 consultId가 같더라도
먼저 소유자를 제한한다. 관리자 메모·자격 증명·게스트 코드는 반환하지 않는다.
Supabase 읽기는 고정 main 행 GET뿐이며, 시간 8초·본문 8 MiB 제한을 유지한다.
자체 JSON 응답은 4 MiB를 넘으면 내용을 자르지 않고 명시적 오류를 반환한다.

보관함 필드와 상담은 **부분 이행 인터페이스**다. 아직 모든 과거 메타데이터나
브라우저에만 남은 상담 기록을 다루지 않는다. 이를 운영 UI에 바로 연결하면 안 된다.
저장 HTML은 JSON 문자열로만 제공한다. 이후 렌더러는 기존 `PJArchiveSecurity.restore`를
반드시 사용해야 하며 raw innerHTML로 넣으면 안 된다.

## 비밀번호 저장 준비

`member-password.cjs`에 비동기 scrypt 생성·검증을 추가했다. 고유 16바이트 임의 salt,
N=32768/r=8/p=3, 64바이트 결과, 고정 버전 형식 `pjo-scrypt-v1$<salt hex>$<digest hex>`를 쓴다.
레코드가 연산 비용을 지정할 수 없으며, 공백·유니코드를 정규화하거나 잘라내지 않는다.
[OWASP 비밀번호 저장 지침](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html),
[Node.js scrypt 문서](https://nodejs.org/api/crypto.html#cryptoscryptpassword-salt-keylen-options-callback).

미래 `passwordHash` 필드가 존재하면 해시만 검증한다. 형식이 잘못되어도 기존 평문으로
되돌아가지 않는다. 현재 `password` 기반 인증과 기존 세션 서명 형식은 호환 유지한다.
해시가 달라지면 기존 회원 세션도 무효가 된다. 집계에 `hashedPassword`를 추가했다.

**해시 생성기를 만들었을 뿐 운영 평문 비밀번호는 바꾸지 않았다.** 기존 브라우저가 평문
비밀번호를 읽으므로 먼저 해시로 바꾸면 로그인이 깨진다. 현재 public app_state가 열려 있어
해시를 먼저 넣는 것도 금지한다. 인증·모든 쓰기 경로·RLS 차단을 함께 준비한 후 전환한다.
이 회원 쿠키는 자체 서명 쿠키이며 Supabase Auth JWT가 아니다.

## 배포/수동 점검 경계

코드 커밋/푸시/배포는 자동 수행하지 않았다. 이 단계 코드는 설정 없이 배포해도 새 API가
503 MEMBER_ACCESS_DISABLED를 반환하고 기존 UI는 그대로다.

점검을 열기로 했을 때에만 Netlify Production / Functions 범위에 설정한다:

- `MEMBER_ACCESS_MODE`: `rehearsal`
- `MEMBER_REHEARSAL_IDS`: `phz` (다른 실사용자 ID를 추가하지 않음)
- `MEMBER_SESSION_SECRET`: 관리자가 별도 생성한 무작위 비밀값. 최소 32자,
  권장 32바이트 이상의 난수. 관리자 키·회원 비밀번호를 재사용하지 않음. Secret으로 보관.

실제 키/비밀번호는 채팅·Git·스크린샷·로그에 남기지 않는다. 기존 관리자 로그인 후 같은
HTTPS 사이트에서 점검해야 한다. `file://`에서는 서버 쿠키가 동작하지 않는다.
설정 후 재배포가 필요하다. 이번 단계는 기존 관리자 UI에 버튼/로그인 폼을 붙이지 않았다.
즉 URL 방문만으로 회원 로그인이 되지 않으며, 점검 클라이언트 연결은 후속 단계다.
점검 후 `MEMBER_ACCESS_MODE=disabled`와 재배포로 새 접근을 다시 닫을 수 있다.

`AI_REQUIRE_MEMBER_SESSION`은 아직 켜지 않는다. 일반 UI가 회원 서버 쿠키를 만들지
않으므로 지금 켜면 정상 회원의 AI 리딩까지 거부된다. Supabase 정책/권한도 아직 회수하지 않는다.

## 남은 Critical과 안전한 다음 단계

1. **본인 자료 쓰기:** 결과 저장·즐겨찾기·상담 전송·가입·회원 수정 등 서버 경로와 모든
   기존 필드 매핑이 필요하다. main JSON 전체를 GET 후 PATCH하는 구현은 다른 회원의 동시
   변경을 덮어쓸 수 있으므로 금지한다. DB 트랜잭션 또는 검증 가능한 원자적 비교/갱신이 필요하다.
2. **운영 인증 전환:** 승인된 백업/복원 시험, 테스트 계정의 전체 작업 점검 후, 브라우저의
   전체 회원 로딩·평문 비밀번호 비교·상태 강제 활성화를 대체한다. 운영 정책은 먼저 확인한다.
3. **공개 DB 접근 차단 + 평문 제거:** 앞 단계와 조율하여 anon/authenticated의 공유 회원
   데이터 직접 접근을 차단한다. 카드 해석 읽기 정책과 혼동하지 않는다. 기존 접근 이력이 있다면
   비밀번호 재설정/사용자 안내 필요성도 검토한다.
4. **공개 로그인 시도 제한:** 이번 API는 관리자 인증 뒤에만 존재한다. 관리자 로그인에
   적용한 Netlify 속도 제한의 실제 배포 적용은 별도 확인해야 한다. 공개 회원 로그인을 열기
   전에는 분산 환경에서 작동하는 로그인 시도 제한이 필요하다. 프로세스 메모리 카운터로 대체하지 않는다.
5. **유료 AI 권한과 사용량:** 회원 서버 인증 연결 후 AI gate와 서버 이용권/사용량 검증을
   켠다. 현재의 IP 제한은 회원 인증이나 총 비용 한도가 아니다.
6. **세션 폐기/재설정:** 로그아웃은 브라우저 쿠키 삭제뿐이다. 복사된 토큰의 즉시 폐기를
   보장하지 않는다. 세션 저장소·회원별 버전/비밀번호 재설정 설계를 보완한다.

실제 사용자 DB 스키마·권한·비밀번호에 영향을 주는 단계는 별도 승인/수동 확인을 요청한다.
