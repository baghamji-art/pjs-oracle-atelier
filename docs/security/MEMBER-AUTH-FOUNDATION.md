## 구현한 것

`netlify/functions/lib/member-auth.cjs`는 HTTP handler 없는 내부 모듈이다.
현재 어떤 운영 함수나 브라우저 코드도 이 모듈을 호출하지 않는다.
새 로그인 URL, 리다이렉트, 활성화 플래그를 만들지 않았다.

- 기존 고정 Supabase URL/서버 키 검사 함수를 재사용한다. 설정 함수 export만
  추가했으며 기존 관리자 연결 확인 동작은 바꾸지 않았다.
- 서버에서만 `app_state`의 main 행 `id,members`를 GET한다.
  기존 JSON 배열 구조 때문에 서버는 전체 회원 배열을 읽어야 하지만,
  그 배열이나 원본 회원 객체를 호출자에게 반환하지 않는다.
- 자격 증명이 맞는 회원의 `{type: 'member', id}`만 명시적으로 반환한다.
  비밀번호, 관리자 메모, 저장 내역, 다른 회원, 원본 오류는 반환/로깅하지 않는다.
- 서버 전용 독립 `MEMBER_SESSION_SECRET` 없이는 동작하지 않는다.
  관리자 서명 키 재사용과 빈 값/짧은 값은 거부한다. 환경변수는 아직 추가하지 않았다.
- 서명된 20분 회원 쿠키에 HttpOnly, Secure, SameSite=Strict와 함수 경로를 지정한다.
  이 쿠키는 Supabase Auth JWT가 아니며 Supabase에 전달해서는 안 된다.
- 회원/관리자 서명 도메인과 쿠키를 분리한다. 위조, 만료, 중복 쿠키,
  잘못된 역할/형식은 DB 조회 전 거부한다.
- 정상 서명도 매 요청마다 회원 존재·상태·만료·비밀번호 변경 여부를 서버에서 재검사한다.
  비밀번호 버전은 비밀키를 사용하는 HMAC이며 공개 비밀번호 해시를 쿠키에 넣지 않는다.
- 읽기 시간 8초, 응답 8 MiB, 회원 수 10,000, ID UTF-8 256바이트,
  비밀번호 UTF-8 4,096바이트 제한 및 중복 ID 거부를 적용했다.
- 데이터 쓰기, 비밀번호 변경/해시 전환, 자동 승인, 영구 회원 전환은 하지 않는다.

Netlify는 하위 디렉터리의 `index` 또는 디렉터리와 이름이 같은 파일을 함수 진입점으로
사용한다. 이 단계의 `lib/member-auth.cjs`에는 그러한 진입점이나 handler가 없다.
[공식 함수 파일 구조 문서](https://docs.netlify.com/build/functions/get-started/)

## 호환성 및 보안상 아직 연결하면 안 되는 이유

1. 운영 브라우저는 여전히 전체 회원 배열과 평문 비밀번호를 읽고 수정할 수 있다.
   서버 인증만 앞에 추가해도 공격자가 그 경로를 이용하면 보호되지 않는다.
2. 본인 리딩 저장, 상담, 가입, 관리자 수정 등 모든 데이터 경로를 서버로 옮긴 후
   공개 DB 권한 차단을 같은 전환 계획 안에서 수행해야 한다.
3. HTTP 로그인 경로를 만들기 전에 분산 환경에서 작동하는 시도 제한,
   요청 본문 크기/출처 검사, 캐시 금지, Cookie를 JSON으로 내리지 않는 응답 어댑터가 필요하다.
4. 현 프런트엔드는 로그인 과정에서 상태/결제를 강제 활성화하고 영구 회원으로 바꾼다.
   새 모듈은 이를 따라 하지 않는다. 허용 상태는 approved/active/expiring_soon이며
   paid=false나 만료된 숫자 expiresAt는 거부한다. expiresAt가 없거나 null인
   허용 상태는 인증할 수 있다. 이용권 부여나 첫 로그인 기간 시작 처리는 별도이다.
   실제 사용자들의 상태·만료 값·ID/비밀번호 길이를 **값을 노출하지 않는 집계**로
   확인하고 전환 정책을 사용자와 결정하기 전에는 연결하지 않는다.
5. 무결성이 확인된 백업으로 별도 환경에서 복원 시험이 필요하다.
   저장 HTML이나 회원 비밀번호를 채팅·로그·Git에 올리지 않는다.
6. 로그아웃 helper는 브라우저 쿠키만 지운다. 복사된 토큰의 즉시 폐기는 제공하지 않는다.
   활성 세션 저장소/폐기 설계 및 재로그인·키 회전 절차가 추가로 필요하다.
7. 비밀번호는 기존 평문 저장 그대로다. 새 모듈의 비교 방식은 저장 암호화/해싱이 아니다.
   공개 접근 차단과 함께 안전한 비밀번호 저장·재설정 계획이 필요하다.
8. 서버가 회원 배열 전체를 읽는 구조는 임시 이행 구조이며 확장성 해결이 아니다.
   새 데이터 쓰기 경로에는 동시 수정 충돌 방지와 권한별 필드 허용 목록이 필요하다.
